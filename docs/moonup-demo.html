MoonUp Rules

A deterministic, embeddable rule engine library for MoonBit. Write business rules as data (Rule / Fact / DSL); the engine handles condition matching, priority-based conflict resolution, and action execution. Same input always yields the same output -- testable, auditable, no LLM hallucination. Embed in CLI, server, WASM browser, or IM bots.

01Use it as a dependency -- minimal example

The core engine (@engine) has zero business semantics. Any MoonBit project can import it and inject its own rule set:

main.mbt
// 1. Define rules: condition DSL + action + priority
let rules = [
  Rule::new("vip_refund", "VIP refund",
    "intent==refund && vip==true",
    "route=vip_agent", 10, "VIP to dedicated agent"),
  Rule::new("normal_refund", "Normal refund",
    "intent==refund",
    "route=self_service", 5, "Self-service flow"),
]

// 2. Build facts (from your business input)
let fact = Fact::new()
fact.set("intent", "refund")
fact.set("vip", "true")

// 3. Execute -- deterministic, testable, auditable
let result = RuleEngine::new(rules).execute(fact)
// result.matched  -> list of matched rules
// result.facts    -> fact snapshot after actions
// result.notes    -> per-rule execution notes (auditable)
Operators: == != ~= (substring) > < >= <=; logic &&. Actions: = (override, higher priority wins) or += (append tag).
02What the engine provides

Deterministic execution

Same rule set + same structured input always yields the same output. No LLM, no hallucination, fully reproducible.

Priority & conflict resolution

When multiple rules match, they execute in priority order. Same-priority ties have a deterministic order -- no runtime randomness.

Auditable

Returns which rules matched, in what order, and which field each action changed. Fact -> Rule -> Action -> Result is fully traceable.

Rules as data

Rules are injected via the MoonBit API, decoupled from engine code. Switching business domains = swapping the rule array, not touching the core.

Embeddable

Zero external dependencies. Compile to native library, CLI tool, or WASM for in-browser execution (this page is proof).

Testable

112 unit tests cover condition matching, conflict resolution, integer parsing edge cases, and rejection of malformed rules. Every rule can be independently asserted.

03Who uses it

Support / ticket routing

  • Route tickets by intent, VIP tier, amount
  • Each business line injects its own rule set

Risk / compliance review

  • Large amount + new customer -> manual review
  • Auditable rules meet compliance requirements

Customer tiering / marketing

  • Tag customers by behavior, region, spend
  • Ops adjusts rules without touching core code

API validation / business rules

  • Consolidate scattered if/else into a maintainable rule set
  • Complements moonrule (JSON schema validation): moonrule checks input validity, this engine decides what to do on match
