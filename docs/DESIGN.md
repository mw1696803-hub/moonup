# MoonUp Rete 设计文档

## 定位

MoonUp 是 MoonBit 的**产生式规则引擎**（Production Rule System），核心基于 Rete 算法。它维护有状态的工作内存（Working Memory），在**多事实**上做条件匹配与跨事实变量绑定，命中后执行动作、修改事实并连锁触发。不做自然语言理解——外层应用把原始输入清洗为结构化 Fact，引擎负责确定性推理。

与 mooncakes.io 已有生态的关系：`moonrule` 是表达式校验引擎（单条 JSON 求值 → 合法/非法，无状态）；MoonUp 是产生式规则引擎（多事实工作内存 → 触发规则 → 执行动作 → 连锁激活，有状态）。二者互补，非重复。

## 设计原则

1. **确定性**：同一规则集 + 同一事实流恒得同一触发序列；冲突消解完全确定，无随机。
2. **增量**：事实 insert/update/retract 时只沿网络传播受影响分支，不做全量重匹配。
3. **共享**：多条规则共享子条件时，alpha 节点只测一次（Rete 的核心收益）。
4. **可审计**：每次执行返回触发轨迹（规则 id、顺序、字段变更），可测试、可追溯。
5. **可组合**：可选决策组件（证据分级、护栏、假设等）建立在引擎之上，按需引入。

## Rete 网络结构

```
                    ┌─────────────────────────────┐
                    │      规则集（条件 → 动作）    │
                    └──────────────┬──────────────┘
                                   │ 编译
                                   ▼
  ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
  │ alpha 节点     │   │ alpha 节点     │   │ alpha 节点     │   ← 单条件测试，共享子条件复用
  │ (单事实条件)   │   │ (单事实条件)   │   │ (单事实条件)   │
  └───────┬───────┘   └───────┬───────┘   └───────┬───────┘
          │                   │                   │
          └─────────┬─────────┘                   │
                    ▼                             │
          ┌───────────────┐                       │
          │  beta 节点     │ ← 跨事实变量绑定 join  │
          │ (join 内存)    │   （如 order × customer）│
          └───────┬───────┘                       │
                  │                               │
                  └──────────────┬────────────────┘
                                 ▼
                       ┌─────────────────┐
                       │ terminal 节点    │ ← 规则完整匹配 → 待触发集合
                       │ (规则 id + token)│
                       └─────────────────┘
```

节点类型：

| 节点 | 作用 | 内存 |
|---|---|---|
| AlphaNode | 单个事实上的原子条件测试（字段 ==/!=/~=/>/</>=/<=） | 通过测试的事实引用 |
| BetaNode | 两个输入的 join：左侧部分匹配 token × 右侧 alpha 事实，按共享变量绑定连接 | 部分匹配 token 列表 |
| TerminalNode | 规则全部条件满足 → 一条完整激活 | 待触发激活（agenda） |

## 匹配流程（match-select-act 循环）

```
insert(fact)
  → 根节点分发到各 alpha 节点
  → 通过测试的 alpha 内存追加事实
  → 向上游 beta 节点传播 → 按变量绑定 join
  → 新 token 沿 beta 链传播 → terminal → agenda

select：冲突消解排序（确定性）
  → salience（规则优先级，大者先）
  → specificity（条件数，多者先）
  → recency（事实新近度，新者先）
  → rule id（字典序，兜底）

act：执行动作
  → 动作可修改/插入/删除事实
  → 事实变化再次进入网络 → 连锁激活
  → fire limit 上限防止死循环
```

## 冲突消解

三层确定性策略（借鉴 Drools 的 salience / specificity / recency）：

1. **salience**：规则的 priority 字段，数值大者先触发；
2. **specificity**：规则的条件数，条件多（更具体）者先触发；
3. **recency**：token 中最新事实的插入序号，序号大者先触发；
4. 仍相同则按规则 id 字典序，保证绝对确定性。

## DSL 设计（v1）

条件（condition）：`<pattern>.<field> <op> <value>`，多个条件用 `&&` 连接。
- pattern：事实类型标记（如 order / customer / device），决定该条件匹配哪类事实；
- field：事实字段；
- op：`==` `!=` `~=`（包含子串）`>` `<` `>=` `<=`；
- value：字面量或变量（`?name`，跨事实绑定）。

动作（action）：`<pattern>.<field>=<value>`（赋值）/ `+=`（追加标签），多个动作用 `&` 连接；特殊动作 `action=<id>` 表示输出触发结果。

示例：
```
order.amount>100000 && customer.is_new==true → action=manual_review (priority=10)
```

## 模块划分

| 模块 | 职责 |
|---|---|
| `lib/rete/` | Rete 网络编译、alpha/beta/terminal 节点、工作内存、增量传播、冲突消解、match-select-act 循环（本仓库核心） |
| `lib/engine/` | 线性匹配模式（规则量小时的简单路径，保留原有 API） |
| `lib/wasm_api/` | WASM 导出：跨事实 demo 输出 |
| `lib/evidence` 等 | 可选决策组件（建立在引擎之上，按需引入） |

## 测试基线

- Rete 网络编译：共享子条件合并、条件错误拒绝；
- 工作内存：insert/update/retract 的增量传播正确性；
- 跨事实 join：变量绑定匹配、无绑定失配、join 内存清理；
- 冲突消解：salience/specificity/recency 排序断言；
- 连锁激活：动作修改事实触发后续规则、fire limit 截断；
- 确定性：同输入两次运行触发序列一致。
