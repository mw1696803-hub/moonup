# MoonUp Rules：MoonBit 可嵌入式确定性规则引擎

**规则即数据**：使用者定义规则集（条件→动作），引擎确定性执行；同一规则集 + 同一结构化事实恒得到同一结果，不做生成式推断。核心是一个与业务语义完全解耦的轻量产生式规则引擎（条件→动作→优先级冲突消解），设计思路参考 Drools / json-rules-engine。mooncakes.io 上已有 `moonrule` 提供 JSON 表达式校验，MoonUp 补的是"命中后执行什么动作"这一层。

## 项目定位

```
┌─────────────────────────────────────────────────┐
│  核心引擎层（零业务语义，可独立使用）              │
│  Rule · Fact · RuleEngine · DSL · 冲突消解        │
├─────────────────────────────────────────────────┤
│  可选决策组件层（按需引入，不依赖核心）            │
│  证据分级 · 护栏检查 · 假设空间 · 案例沉淀        │
├─────────────────────────────────────────────────┤
│  使用者注入的规则集（任意业务领域）               │
│  客服分流 / 风控审核 / 客户分层 / 工单路由 …      │
└─────────────────────────────────────────────────┘
```

**技术哲学**：LLM 负责自然语言理解，规则引擎负责确定性判断。外层应用把原始输入清洗为结构化 Fact，引擎执行可测试、可审计、可复现的决策路径。

## 是什么

MoonUp 是 MoonBit 生态的确定性规则引擎库：

- **`engine`** 提供规则即数据的核心（条件 DSL、动作、优先级冲突消解、确定性执行）；
- **可选决策组件**（证据分级、护栏检查、假设空间、案例沉淀）建立在引擎之上，按需引入；
- 使用者通过注入自己的规则集来服务任意业务场景。

**解决什么问题**：业务规则（客户分层、客服分流、风控审核、API 校验）散落在代码与个人经验里，不可测试、不可审计。MoonUp 把规则数据化、执行确定性，让"判断"可测试、可复现。

## 最小示例

```moonbit
// 1. 定义规则：条件 DSL + 动作 + 优先级
let rules = [
  Rule::new("vip_refund", "VIP退款",
    "intent==refund && vip==true",
    "route=vip_agent", 10, "VIP转专属坐席"),
  Rule::new("normal_refund", "普通退款",
    "intent==refund",
    "route=self_service", 5, "走自助流程"),
]

// 2. 构造事实（来自你的业务输入）
let fact = Fact::new()
fact.set("intent", "refund")
fact.set("vip", "true")

// 3. 执行——确定性、可测试、可审计
let result = RuleEngine::new(rules).execute(fact)
// result.matched  → 命中的规则列表
// result.facts    → 执行动作后的事实快照
// result.notes    → 每条规则的执行说明（可审计）
```

支持的条件运算符：`==` `!=` `~=`（包含子串）`>` `<` `>=` `<=`；逻辑组合 `&&`。动作为 `=`（覆盖，高优先级胜出）或 `+=`（追加标签）。

## 三个不同领域示例（同一引擎）

```moonbit
// 客服分流
Rule("cs1", "VIP退款", "intent==退款 && vip==true", "route=VIP人工坐席", 10, "VIP退款转专属坐席")

// 风控审核
Rule("rk1", "大额新客", "amount>100000 && new_customer==true", "action=人工复核", 10, "大额+新客强制人工")

// 客户分层
Rule("t1", "高价值客户", "intent~=高 && region==华东", "tier=高价值客户", 10, "高意向+华东")
```

三个示例共用同一个 `RuleEngine` 核心，只换规则数组，引擎代码零改动。

## 模块

| 模块 | 能力 |
|---|---|
| `engine` | 通用规则引擎核心：Rule（条件 DSL）+ Fact（键值事实）+ RuleEngine（匹配/执行/优先级冲突消解）+ 标签累积 |
| `evidence` | 可选组件：来源分级与置信度合成 |
| `guardrail` | 可选组件：规则触发前的检查护栏 |
| `hypothesis` | 可选组件：候选假设生成与优先级 |
| `scenario` | 可选组件：配置驱动的场景路由 |
| `case` | 可选组件：案例标签检索、JSON 落盘、反馈闭环 |
| `ogsm` | 可选组件：结构化输入清洗 |
| `output` | 可选组件：结构化报告模板 |

核心 `engine` 不依赖任何可选组件；单独引入 `engine` 即可使用完整的规则执行能力。

## 原创 / 参考说明

- 全部代码以 MoonBit 从零实现，MIT 许可证；
- 引擎设计参考成熟生态中的规则引擎标准件（仅参考设计思想，未使用其代码）：
  - [Drools](https://github.com/apache/incubator-kie-drools)（Apache-2.0）：Java 生态规则引擎
  - [json-rules-engine](https://github.com/CacheControl/json-rules-engine)（ISC）：JS 生态轻量规则引擎
- 与上述项目的差异：
  - 轻量 DSL，不引入重型规则语言，适合 WASM 与嵌入式场景；
  - 零外部依赖，纯 MoonBit 核心库，可被任意形态应用嵌入；
  - 与 moonrule（JSON 表达式校验）互补：moonrule 管输入合不合法，本引擎管命中后做什么。

## AI 使用说明

本项目在开发过程中使用了 AI 辅助编程工具，符合赛事「AI 可解释」要求。

**AI 参与范围**：模块脚手架与部分函数实现、接口设计辅助、边界测试用例生成、文档起草润色。

**参赛者掌握并负责的部分**：架构设计、技术选型、代码审查与测试验证——所有 AI 生成代码经逐条审查，112 个单元测试与端到端 Demo 验证通过。

**关键技术选择：为什么用确定性规则引擎，而非 LLM 直接输出**
- **可测试**：每条推理路径可被单元测试覆盖；
- **无幻觉**：不生成规则之外的判断；
- **可审计**：命中规则、执行顺序、字段变更全部可追溯；
- **可嵌入**：纯 MoonBit 核心库，可被 CLI、Web、WASM 等任意形态应用嵌入。

LLM 的角色：自然语言理解留在外层应用，不在本仓库范围内；核心判断逻辑保持确定性。
